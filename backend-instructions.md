# Backend instructions

Документ описывает, какие части аутентификации сейчас реализованы во
фронтенд-репозитории как **временный мок** и должны быть заменены настоящим
бекендом, а также жёстко фиксирует контракт HTTP-API, на который завязан
фронт. Контракт менять можно — но любое изменение требует синхронной правки
схем в `src/entities/user/model/user.schema.ts`.

> Если поведение бекенда расходится с этим документом, **правда — фронт**:
> фронтенд парсит каждый ответ через Zod и упадёт на несоответствии типов.

## Общие требования к бекенду

### Сессии — HTTP-only cookie

- Имя cookie: **`session`** (захардкожено в `src/app/api/auth/_lib/constants.ts`,
  используется фронтовым `middleware.ts`). Если решите переименовать —
  правьте оба места.
- Атрибуты cookie:
  - `HttpOnly` — обязательно;
  - `Secure` — на проде обязательно;
  - `SameSite=Lax`;
  - `Path=/`;
  - `Max-Age` соответствует TTL сессии (по дефолту 7 дней).
- Значение cookie — **opaque session id** (например, 32 байта рандома в hex).
  Можно JWT, но это не обязательно: фронт значение не парсит и не читает,
  только пересылает.
- Сессии серверного состояния: храните в БД/Redis с TTL. На каждом запросе
  валидируйте сессию (не просрочена, юзер существует, не заблокирован).

### CORS (если бекенд на другом домене)

- `Access-Control-Allow-Origin` = конкретный origin фронта (не `*`).
- `Access-Control-Allow-Credentials: true` — иначе браузер не отправит cookie.
- `Access-Control-Allow-Headers: Content-Type`.
- Разрешённые методы: `GET, POST, OPTIONS`.

Фронт уже шлёт `credentials: 'include'` (`src/shared/api/http.ts`).

### Формат ошибок

Любая 4xx/5xx должна возвращать JSON-тело вида:

```json
{ "error": "Human-readable code or message", "attemptsLeft": 3 }
```

- Поле `error` — строка. Фронт сейчас не отображает её напрямую (мапит
  по HTTP-статусу), но в логах увидеть полезно.
- Дополнительные поля разрешены и парсятся, если фронт умеет их прочитать.
  Сейчас единственный такой случай — `attemptsLeft` в ответе 422 на
  `register/verify` (см. ниже).

Фронт-обработчик: `src/shared/api/api-error.ts` — ловит status, url, payload.

### Безопасность (не пересказ OWASP, но напомню)

- Пароли хешировать **argon2id** (предпочтительно) или scrypt. Никогда не
  bcrypt с дефолтными параметрами в 2026 году. Никогда не md5/sha256
  без kdf. Сейчас в моке используется scrypt — этого мало для продакшна.
- Rate-limit на `/auth/login`, `/auth/register/start`,
  `/auth/register/verify` — минимум по IP, лучше также по email/challengeId.
- Защита от user enumeration:
  - 401 на login: одинаковый текст на "нет такого юзера" и "неверный пароль".
  - 409 на `register/start` для занятого email — допустим (фронт показывает
    "email уже зарегистрирован"). Если для вас это утечка, можно вместо
    409 возвращать тот же 202, но **никаких писем не слать**. Тогда фронт
    покажет "проверьте почту", а зайти будет невозможно. Сейчас фронт
    ожидает 409 и показывает понятный текст. Если хотите менять политику —
    скажите, поправлю.
- Защита от подбора кода подтверждения:
  - Максимум 5 попыток на challenge (сейчас на моке стоит так).
  - TTL кода — 10 минут.
  - 6-значный код. Если хотите 8 — поменяйте regex в
    `src/entities/user/model/user.schema.ts`.
- Логирование: не пишите пароли/коды в логи (мок пишет код в консоль — это
  только для дева). На проде — `console.log` строки `[auth/mock] verification code` быть не должно.

## Контракт API

База: `${NEXT_PUBLIC_API_BASE_URL}` (в dev = `http://localhost:3000/api`,
в проде = адрес бекенда, например `https://api.example.com`).

Все запросы и ответы — `application/json; charset=utf-8`.

### Общий тип `User`

```ts
type User = {
  id: string; // uuid v4 или любой стабильный идентификатор
  email: string; // нормализованный (trim + lowercase)
  name: string; // отображаемое имя, не пусто
  createdAt: string; // ISO 8601 UTC, например "2026-05-22T13:45:00.000Z"
};
```

Схема: `UserSchema` в `src/entities/user/model/user.schema.ts`.

---

### POST `/auth/login`

Логин по email и паролю. Никаких подтверждений.

**Request body:**

```ts
type LoginInput = {
  email: string; // валидный email
  password: string; // непустая строка
};
```

**Ответы:**

| Статус | Тело                                                          | Когда                                |
| ------ | ------------------------------------------------------------- | ------------------------------------ |
| `200`  | `{ "user": User }` + `Set-Cookie: session=...; HttpOnly; ...` | Успех                                |
| `400`  | `{ "error": "Invalid body", "details": ... }`                 | Невалидное тело (Zod-ошибки и т.п.)  |
| `401`  | `{ "error": "Invalid email or password" }`                    | Юзер не найден ИЛИ пароль не подошёл |
| `429`  | `{ "error": "Too many attempts" }`                            | Rate-limit                           |
| `5xx`  | `{ "error": "..." }`                                          | Прочие сбои                          |

**TypeScript-тип успеха:**

```ts
type LoginResponse = { user: User };
```

Схема: `LoginInputSchema`, `LoginResponseSchema`.

**Поведение:**

- Email нормализовать (trim + lowercase) перед сравнением в БД.
- Время ответа должно быть примерно одинаковым для "юзер не найден" и
  "неверный пароль" (защита от user enumeration по таймингу). Сравнение
  пароля через `timingSafeEqual` или эквивалент.
- При успехе создать сессию, поставить cookie `session`. Сессии,
  действовавшие до этого логина, можно либо инвалидировать ("один активный
  сеанс на устройство"), либо оставить (мульти-устройства) — фронт это не
  парсит, на ваше усмотрение.

---

### POST `/auth/logout`

Закрывает текущую сессию.

**Request body:** пусто.

**Ответы:**

| Статус | Тело   | Действие                                                                 |
| ------ | ------ | ------------------------------------------------------------------------ |
| `204`  | `null` | + `Set-Cookie: session=; Max-Age=0; HttpOnly; Path=/` (cookie очищается) |

Даже если cookie не пришло или сессия уже мертва — отвечать `204` (идемпотентно).

---

### GET `/auth/me`

Возвращает текущего пользователя по cookie.

**Request:** нет тела. Сессия определяется по cookie `session`.

**Ответы:**

| Статус | Тело                                       | Когда                                        |
| ------ | ------------------------------------------ | -------------------------------------------- |
| `200`  | `User` (плоско, без обёртки `{user: ...}`) | Сессия валидна                               |
| `401`  | `{ "error": "Unauthorized" }`              | Нет cookie / сессия просрочена / юзер удалён |

**Важно:** в отличие от `/auth/login`, тут `User` возвращается **без**
обёртки `{ user: ... }` — фронт парсит ответ напрямую через `UserSchema`.

```ts
// fetch('/auth/me') -> User | 401
```

**Кэширование:** ответ — per-request, никогда не кэшировать
(`Cache-Control: no-store`). Фронт уже шлёт `cache: 'no-store'` для
серверного `getMe`.

### POST `/auth/register/start`

Шаг 1 регистрации. Сервер валидирует данные, **создаёт временный
challenge**, отправляет 6-значный код на email, возвращает `challengeId`.

**Request body:**

```ts
type RegisterStartPayload = {
  name: string; // ≥ 2 символа
  email: string; // валидный email, ещё не зарегистрированный
  password: string; // ≥ 8 символов, содержит хотя бы одну букву и одну цифру
};
```

Фронтовая валидация дублируется в `RegisterStartInputSchema`. На бекенде —
обязательно валидировать ещё раз (фронт можно обойти).

**Ответы:**

| Статус | Тело                                                                 | Когда                                                     |
| ------ | -------------------------------------------------------------------- | --------------------------------------------------------- |
| `202`  | `{ "challengeId": string, "email": string, "expiresInSec": number }` | Код отправлен                                             |
| `400`  | `{ "error": "Invalid body", "details": ... }`                        | Валидация не прошла                                       |
| `409`  | `{ "error": "Email already registered" }`                            | Email уже зарегистрирован                                 |
| `429`  | `{ "error": "Too many attempts" }`                                   | Rate-limit (например, > 3 раз в минуту с одного IP/email) |

**TypeScript-тип успеха:**

```ts
type RegisterStartResponse = {
  challengeId: string; // непустая строка, opaque id
  email: string; // тот же email из запроса, нормализованный
  expiresInSec: number; // положительное целое, например 600
};
```

Схема: `RegisterStartPayloadSchema`, `RegisterStartResponseSchema`.

**Поведение:**

1. Валидировать тело.
2. Если email уже зарегистрирован → `409` **без** отправки письма.
3. Сгенерировать `challengeId` (uuid/opaque), `code` (6 цифр).
4. Сохранить в БД/Redis: `challengeId → { email, name, passwordHash, code, expiresAt, attemptsLeft = 5 }`.
   **Пароль хешировать сразу же**, plain-текст пароля никуда не сохранять
   и никуда не возвращать.
5. Отправить письмо с кодом.
6. Вернуть `202` с `challengeId`, эхом email и `expiresInSec` (TTL кода
   в секундах, например `600`).

**Что фронт делает с этим:**

- Кладёт `challengeId` в локальный state экрана (не в localStorage,
  не в Zustand, исчезает при перезагрузке вкладки).
- Запускает обратный отсчёт по `expiresInSec` — пользователь видит
  оставшееся время.
- Показывает экран ввода кода с email, который пришёл в ответе.

### POST `/auth/register/verify`

Шаг 2 регистрации. Подтверждает код, создаёт пользователя, открывает сессию.

**Request body:**

```ts
type RegisterVerifyInput = {
  challengeId: string; // тот же, что вернул /auth/register/start
  code: string; // ровно 6 цифр, например "048213"
};
```

**Ответы:**

| Статус | Тело                                                          | Когда                                          |
| ------ | ------------------------------------------------------------- | ---------------------------------------------- |
| `201`  | `{ "user": User }` + `Set-Cookie: session=...; HttpOnly; ...` | Успех. Юзер создан, сессия открыта             |
| `400`  | `{ "error": "Invalid body", "details": ... }`                 | Не прошла валидация payload-а                  |
| `404`  | `{ "error": "Challenge not found" }`                          | `challengeId` неизвестен (или email уже занят) |
| `410`  | `{ "error": "Code expired" }`                                 | TTL истёк                                      |
| `422`  | `{ "error": "Wrong code", "attemptsLeft": number }`           | Код неверный, попытки ещё есть                 |
| `429`  | `{ "error": "Too many attempts" }`                            | Попытки кончились — challenge закрыт           |

**TypeScript-тип успеха:**

```ts
type RegisterVerifyResponse = { user: User };
```

Схема: `RegisterVerifyInputSchema`, `RegisterVerifyResponseSchema`.

**Важно про обработку статусов:** фронт мапит статусы в тексты:

- `422` → "Неверный код. Осталось попыток: N." (берёт `attemptsLeft` из тела).
- `410` → "Срок действия кода истёк. Начните регистрацию заново."
- `429` → "Слишком много попыток. Начните регистрацию заново."
- `404` → "Сессия регистрации не найдена. Начните заново."

Если бекенд будет возвращать другой статус — фронт покажет дефолтный текст
"Не удалось подтвердить код. Попробуйте позже". Менять маппинг — в
`src/features/auth-register-form/ui/verify-step.tsx::formatError`.

**Поведение бекенда:**

1. Найти challenge по `challengeId`.
2. Если не найден → `404`.
3. Если просрочен → удалить запись, вернуть `410`.
4. Если `attemptsLeft <= 0` → удалить запись, вернуть `429`.
5. Сверить код:
   - Не совпал → `attemptsLeft--`. Если стало 0 → удалить запись, вернуть
     `429`. Иначе → вернуть `422` с актуальным `attemptsLeft`.
   - Совпал →
     - Race-check: если email уже зарегистрирован (вторая вкладка успела) →
       удалить challenge, вернуть `404`.
     - Создать пользователя в БД (email, name, passwordHash из challenge).
     - Создать сессию, поставить cookie.
     - Удалить challenge.
     - Вернуть `201` с `{ user }`.

## Email-отправка кода

На моке кода никто никуда не шлёт — он печатается в консоль
(`src/app/api/auth/register/start/route.ts`, строка с `console.log`). На
бекенде нужно:

- Шаблон письма (HTML + plain-text).
- Тема: "Код подтверждения для регистрации в Тендеры" или похожее.
- В теле — 6-значный код и срок действия в человекочитаемом виде ("10 минут").
- Адрес отправителя — корпоративный, не `noreply@yourdomain.com` без
  SPF/DKIM/DMARC.
- Очередь / ретраи на случай временной недоступности SMTP/SES.

## Чек-лист для бекенд-разработчика

- [ ] Эндпоинты в точности соответствуют контракту выше (URL, методы,
      статусы, форма body).
- [ ] Cookie `session` ставится с `HttpOnly`, `Secure` (на проде),
      `SameSite=Lax`, `Path=/`, `Max-Age=7d`.
- [ ] CORS настроен под фронт-домен с `credentials: true` (если разные
      хосты).
- [ ] Пароли хешируются argon2id / scrypt с осмысленными параметрами.
- [ ] Rate-limit на `/auth/login`, `/auth/register/start`,
      `/auth/register/verify`.
- [ ] User enumeration по таймингу login защищён.
- [ ] Email с кодом действительно уходит (не только при `NODE_ENV=production`,
      и в стейджинге тоже).
- [ ] `GET /auth/me` отвечает `Cache-Control: no-store`.
- [ ] Логи не содержат паролей, кодов и сессий в открытом виде.
- [ ] При удалении пользователя или смене пароля — все его сессии
      инвалидируются (это уже за пределами текущего фронта, но потребуется).
- [ ] `Set-Cookie` на `/auth/logout` действительно затирает cookie
      (Max-Age=0, тот же Path).

## Что фронт делает после переключения

1. Прописать в `.env.production` (или где у вас сейчас) реальный
   `NEXT_PUBLIC_API_BASE_URL`.
2. Удалить файлы из таблицы в начале документа.
3. Проверить, что `src/middleware.ts` всё ещё импортирует
   `SESSION_COOKIE` из `src/app/api/auth/_lib/constants.ts` — если папка
   `src/app/api/auth/` удалена целиком, **перенести** константу в
   `src/shared/config/`, иначе билд упадёт.
4. `npm run check && npm run build`.
